# Noon UAE/KSA 实时库存采集器设计

日期：2026-08-07  
状态：已确认

## 目标

每天北京时间 08:00，使用六个 Noon 店铺的 API JWT 凭据，分别获取 UAE 与 KSA 当时的实时 FBN 库存，生成下游库存更新流程需要的十二个 CSV 文件。采集过程不依赖影刀 RPA、Chrome 登录、网页国家切换或邮箱验证码。

本采集器与现有 09:00 库存工作簿更新任务分离：本任务负责可靠地产出当天源文件；下游任务负责备份和更新 UAE/KSA 工作簿。后续合并时，两者通过本文定义的文件契约衔接。

## 已验证结论

六份凭据位于 `D:\noon-api`，并与店铺一一对应：

| 文件 | 项目代码 | 店铺 |
|---|---|---|
| `noon1-API.json` | `PRJ42958` | 店铺1 |
| `noon2-API.json` | `PRJ55651` | 店铺2 |
| `noon3-API.json` | `PRJ61683` | 店铺3 |
| `noon4-API.json` | `PRJ65553` | 店铺4 |
| `noon5-API.json` | `PRJ75299` | 店铺5 |
| `noon6-API.json` | `PRJ363826` | 店铺6 |

店铺1已经完成端到端只读验证：

- API JWT 登录返回 HTTP 200。
- API 会话可以直接调用 Noon Seller Lab 网页使用的实时库存接口。
- 接口返回 `text/csv`，字段与网页 `My Inventory -> Export` 下载一致。
- UAE 测试文件只有项目 `42958` 和国家代码 `AE`。
- 实时 CSV 的可售数量合计为 `3435`，与页面显示值完全一致。

官方 Reports API 的 Aging、Ledger Summary 和 Ledger Detailed 报表已排除作为实时主数据源：它们分别提供日快照、月度/日度汇总和历史流水，不能稳定等同 08:00 时点的实时库存。

## 数据采集架构

采集器使用“官方认证 + Seller Lab 实时只读接口”：

1. 读取某店铺的 API JSON 凭据。
2. 使用 `key_id` 和 `private_key` 生成 RS256 JWT。
3. 调用 Noon Identity 登录接口建立带 Cookie 的会话：
   `POST https://noon-api-gateway.noon.partners/identity/public/v1/api/login`
4. 以对应 `project_code` 调用实时库存导出接口：
   `POST https://fbn.noon.partners/_svc/sc-fbn/api/v5/seller-lab/fbn-inventory`
5. 请求体固定为：
   `{"inventory_tab_name":"export"}`
6. UAE 使用 `X-Locale: en-ae`，KSA 使用 `X-Locale: en-sa`。
7. 请求必须同时带 `X-Platform: web`、准确的 `X-Project`、小写站点 `Country-Code`（`ae`/`sa`）和数值店铺 `Id-Partner`。后两项是 Noon 库存页真正用于国家和店铺筛选的请求头；仅改变 URL 或 `X-Locale` 会让 KSA 请求错误返回 UAE 数据。
8. 将响应先写入站点临时目录，完成全套校验后再发布到当天正式目录。

实时接口属于 Noon 网页内部接口，不是公开 API Reference 的稳定契约。采集器必须将接口变化视为显式失败，不能静默回退到前一天 Aging 快照。

## 输出契约

### 目录

- UAE：`D:\文件\库存文件\UAE\YYYY-MM-DD\`
- KSA：`D:\文件\库存文件\KSA\YYYY-MM-DD\`

日期按 `Asia/Shanghai` 的运行日期计算，目录不存在时创建。

### 文件名

- UAE：`UAE1.YYYYMMDD.csv` 至 `UAE6.YYYYMMDD.csv`
- KSA：`SA1.YYYYMMDD.csv` 至 `SA6.YYYYMMDD.csv`

KSA 使用 `SA` 前缀，以匹配已经确认的下游库存更新契约。

### 必需字段

采集器保留 Noon 返回的完整 CSV，不主动删减字段。发布前至少要求存在：

- `inventory_type`
- `partner_sku`
- `qty`
- `id_partner`
- `inventory_snapshot_at`
- `country_code`

下游只依赖前三个字段：筛选 `inventory_type = saleable`，按 `partner_sku` 汇总 `qty`。保留完整响应可以兼容现有文件并为排障提供证据。

## 站点和店铺校验

每个文件必须同时通过以下检查：

1. HTTP 状态为 200，响应类型为 CSV，响应体非空。
2. CSV 可以按 RFC 4180 规则解析，包括引号、字段内逗号和 CRLF。
3. 必需字段全部存在且不重复。
4. `id_partner` 只能等于当前凭据对应的店铺编号。
5. UAE 的 `country_code` 只能为 `AE`；KSA 只能为 `SA`。
6. `inventory_snapshot_at` 必须属于当天实时窗口；默认要求与请求完成时间相差不超过 60 分钟。
7. 至少存在一条 `saleable` 记录。
8. `saleable` 记录的 `partner_sku` 非空，`qty` 是非负有限数值。
9. 记录行数、可售 SKU 数和可售数量必须大于零，并写入运行摘要。

任一检查失败，该店铺文件不发布。某站点只有六个店铺全部通过时才视为站点成功。

## 执行、重试与幂等

正式任务每天 08:00 执行一次，时区固定为 `Asia/Shanghai`，并禁止同一任务并发运行。

每个店铺最多尝试三次：首次失败后等待 30 秒，第二次失败后等待 90 秒。以下情况允许重试：网络超时、HTTP 429、HTTP 5xx 和临时下载失败。认证失败、项目不匹配、国家不匹配、字段变化和快照过期不自动反复重试。

所有响应先保存到本次运行的 staging 目录。六份文件全部校验通过后，才发布到目标日期目录。当天重复运行时，新文件同样必须完整通过校验；发布过程替换同名文件，但不得在验证成功前覆盖已有有效文件。

如果某个站点失败，另一个站点继续执行。失败站点不得使用前一天文件、官方日快照或部分成功文件冒充当天完整结果。

## 通知

成功和失败都发送企业微信群机器人通知。Webhook 只能从本机安全配置或环境变量 `WECOM_WEBHOOK_URL` 读取，不能写入仓库、日志或错误堆栈。

成功通知包含：

- 运行日期、开始和结束时间。
- UAE/KSA 各自成功状态。
- 每个店铺的文件名、快照时间、总行数、可售 SKU 数和可售数量。

失败通知包含：

- 站点、店铺、失败阶段和最终错误类别。
- 已执行次数。
- 是否存在可继续供下游使用的完整旧文件集。

通知中不得包含 API Cookie、JWT、私钥、完整响应头或企业微信 Webhook。

## 密钥安全

- `D:\noon-api\*.json` 是长期敏感凭据，只允许本机运行账号读取。
- 程序不得打印、复制、上传或提交 `private_key`、`key_id`、Cookie 或 JWT。
- Git 忽略规则必须覆盖凭据文件、临时 Cookie、staging 输出和原始调试响应。
- 日志只记录凭据文件编号和 `project_code`，不记录密钥内容。
- API 私钥泄露时必须在 Noon API Users 中撤销并重新生成。
- 之前在聊天中暴露的邮箱密码和企微 Webhook 应由用户轮换；本方案不再需要邮箱密码或 Outlook OAuth。

## 与 09:00 下游任务的衔接

下游任务的输入约束保持不变：

- UAE/KSA 分别要求六个同日期文件全部存在。
- 必须存在 `inventory_type`、`partner_sku` 和 `qty`。
- 只聚合 `saleable`，并按 `partner_sku` 求和。
- UAE 和 KSA 独立失败。

本地 `D:\文件\库存文件` 不是 OneDrive 重解析点。当前采集器范围止于生成本地十二个 CSV；与云端 Power Automate 合并时，必须明确增加“同步到下游 OneDrive 目录”步骤，或将下游正式源目录改为可访问本地文件的执行方式。不得假设本地目录会自动出现在 OneDrive。

## 日志与可观测性

每次运行生成结构化日志，记录：

- `run_id`、站点、店铺编号、项目代码。
- 认证、请求、解析、校验、发布、通知各阶段状态。
- HTTP 状态码、耗时、重试次数。
- 快照时间、数据行数、可售 SKU 数和可售数量。
- 脱敏后的错误类别和消息。

日志按日期轮转，默认保留 30 天。原始 CSV 是业务输出，不作为调试日志删除。

## 测试策略

### 单元测试

- 六份凭据与项目代码映射。
- UAE/SA 文件命名和日期格式。
- JWT 声明和 RS256 签名结构，不使用真实密钥 fixture。
- CSV 引号、逗号、BOM、CRLF 和异常结构解析。
- 店铺、国家、快照窗口、必需字段与数值校验。
- 重试分类、退避和幂等发布。
- 企微通知内容脱敏。

### 集成测试

- 店铺1 UAE 实时导出并与页面总可售数量核对。
- 店铺1 KSA 实时导出并验证 `SA`。
- 六店 UAE 和六店 KSA 全量 dry run，输出到临时目录。
- 模拟单店认证失败、429、5xx、CSV 字段变化和过期快照。
- 验证失败时不会发布部分站点文件，也不会读取旧日期目录。

### 联调测试

- 将采集结果交给 09:00 下游测试流程。
- 验证六个文件与店铺1至店铺6映射正确。
- 验证下游 `saleable` 聚合结果与采集摘要一致。
- 验证新增 SKU、售罄 SKU 和零库存规则。
- 验证 08:00 采集失败时，09:00 下游不会更新该站点工作簿。

## 验收标准

1. 每天 08:00 自动运行且无重叠实例。
2. 不启动 Chrome，不读取邮箱验证码，不调用影刀。
3. 十二个文件使用正确站点、店铺和日期命名。
4. 每个文件的项目、国家和实时快照通过校验。
5. 店铺1 UAE 的可售数量与 Seller Lab 页面一致；其余店铺按相同口径验证。
6. 单店或单站点失败时不发布伪造、过期或不完整的数据集。
7. 成功和失败均发送脱敏企微通知。
8. API 凭据、JWT、Cookie 和 Webhook 不出现在代码仓库及日志中。
9. 09:00 下游流程可直接读取产出的 CSV 并正确汇总可售库存。
10. 内部接口变化时任务明确失败并通知，不降级到非实时数据。
